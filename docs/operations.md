# 运行配置

项目配置文件名为 `opencook.json` 或 `opencook.jsonc`，项目配置目录为 `.opencook/`。公开示例是根目录的 `opencook.example.json`；个人配置文件受 Git 忽略规则保护。项目文件包含模型服务 `cooking_models`，以及权限、MCP、联网搜索等通用配置。模型不再从供应商目录定义读取。

用户数据、配置、缓存和状态目录使用 `opencook` 名称。模型设置和 API Key 写入设置页显示的 `opencook.json`（已有 JSONC 文件也保留支持）。设备设置、个人记忆和会话位于本地数据库，摄像头密码仍保存在凭据存储中。终端偏好位于 `~/.config/opencook/cli.json`。配置环境变量统一为 `OPENCOOK_*`。JSON Schema 随仓库保存在 `docs/schemas/`；产品不依赖托管网站提供配置校验。

内部包命名为 `@opencook/*`，SDK 使用 `OpenCook`。当前只提供终端产品及其服务和开发库，未包含其他产品的桌面端、商业控制台、营销网站或部署任务。MCP OAuth 默认使用动态客户端注册；自部署方可以通过 `OPENCOOK_OAUTH_CLIENT_METADATA_URL` 提供自己的公开元数据文档。

## 终端界面

首页保留聊天输入框，显示随窗口大小缩放的 `OpenCooK` 字标和轻量蒸汽字符动画。打开 `Ctrl+P` 后可用中英文搜索内置命令及设置，包括 `Skills 技能`、`Prompt 输入`、会话、主题和服务连接；条目、对话框及操作提示采用英文在前、中文在后的标签。技能、主题和服务的自定义名称保持原值。

在 `Settings 设置 → Animations 动画` 中关闭动画后，蒸汽图案静止。缩小窗口时字标自动紧凑显示，优先留出输入空间；深色、浅色和自定义主题切换立即生效。主题可通过 `text.brand` 指定字标颜色，旧主题不填写此字段也可使用。自定义品牌色与背景对比不足时，字标使用主题正文色以保持可读。

## 模型服务

终端设置采用英文在左、中文在右的双语标签，例如 `Model services 模型服务`。打开 `Settings 设置`，进入「模型服务」。分别配置文本对话、多模态视觉、语音合成 TTS、Embedding、Rerank 的启用状态、服务基础地址、模型名称和 API Key。文本与视觉服务使用 OpenAI Chat Completions 兼容接口；对话模型必须支持工具调用。上下文长度必须大于输出上限。

在设置中保存后，五类模型的配置及 API Key 写入同一配置文件的 `cooking_models.chat/vision/speech/embedding/rerank`；普通设置接口及模型目录只返回 `has_key`，不返回密钥。输入界面使用掩码，清除密钥需单独选择「清除 API Key」。文件以仅当前用户可读写的权限原子替换，保留其他配置及 JSONC 注释。文本与视觉路由自动刷新；手工修改文件也会在下一次配置刷新时生效。

服务启动时固定配置文件路径：显式 `OPENCOOK_CONFIG` 优先，否则从启动目录向上寻找已有的 `opencook.jsonc` / `opencook.json`，找不到配置但上级目录有 `opencook.example.json` 时，在该示例旁创建 `opencook.json`；否则使用用户配置目录下的 `opencook.json`。所有客户端通过设置页显示的路径修改同一份配置。首次升级会将旧数据库中的五类模型及密钥迁入未配置模型的文件，随后文件成为唯一配置来源；清空或删除某个模型项不会从旧数据库恢复密钥。对话传输所用凭据是根据文件同步的缓存。公开分发使用无个人配置的 `opencook.example.json`，勿提交个人配置。

语音合成 TTS 已接入烹饪指导。Embedding 和 Rerank 已有独立文件配置入口，向量检索流水线尚未接入。现有知识检索仍使用下文的词法匹配；保存 Embedding/Rerank 设置不会自动将它改成向量检索。

未保存用户文本模型设置时，也可在启动服务端的环境中设置以下变量：

| 变量                      | 含义                                                               |
| ------------------------- | ------------------------------------------------------------------ |
| `OPENCOOK_MODEL_BASE_URL` | 实际部署的 OpenAI Chat Completions 兼容服务地址，包含 API 基础路径 |
| `OPENCOOK_MODEL_ID`       | 服务内部使用的真实模型 ID                                          |
| `OPENCOOK_MODEL_API_KEY`  | 服务端凭据；本地无认证服务可以不设置                               |
| `OPENCOOK_MODEL_CONTEXT`  | 实际上下文上限，默认 128000，需按部署模型核实                      |
| `OPENCOOK_MODEL_OUTPUT`   | 实际输出上限，默认 8192，必须小于上下文上限                        |

没有用户配置、环境地址或模型 ID 时，不会注册可用的对话模型。已保存的用户配置优先，包括明确停用模型；此时不会使用环境中的运营方凭据兜底。对话使用 `opencook/cook` 别名，已启用的视觉服务使用独立的 `opencook-vision/vision` 路由。常规工作区配置不加载模型供应商定义或替换内置角色。

终端的 `run`、`mini` 不接受 `--model`、`--agent`；`models` 命令已移除。原更新器和 ACP 命令也已移除。正式产品的网关部署、用户身份认证和发布流程仍需单独建设；不要将运营方共享凭据打进分发给用户的二进制。

### 学校模型示例

华东师范大学服务的基础地址为 `https://chat.ecnu.edu.cn/open/api/v1`。用途与模型名对应如下，实际可用模型以服务的 `/models` 接口及[官方模型文档](https://developer.ecnu.edu.cn/vitepress/llm/model.html)为准：

| 用途                           | 模型名称               |
| ------------------------------ | ---------------------- |
| 文本对话、规划、菜谱生成及文档 | `ecnu-max`             |
| 图片理解与视觉检测             | `ecnu-plus`            |
| 语音合成 TTS                   | `ecnu-tts`             |
| 文本向量                       | `ecnu-embedding-small` |
| 文本重排                       | `ecnu-rerank`          |

这些接口使用同一学校账号的令牌，在不同用途的本地配置中分别保存。语音功能指文字转语音播报（TTS），产品当前不配置语音识别。上述名称和地址可公开，个人令牌保存在受 Git 忽略规则保护的私有配置文件。

Cook 组装本次请求时检查实际对话上下文：纯文本上下文使用文本配置；包含用户图片或工具返回的图片时使用已配置的视觉路由。模型切换在请求准备之前完成，图像能力检查、用量记录和供应商上下文均使用实际调用的模型。摄像头的确定性采样、温度计算和 OpenCV 翻炒判定不随模型切换改变。

聊天缺少模型时会直接打开包含五类模型的「模型服务」。联网搜索和网页读取的授权入口位于 Settings →「联网搜索与网页服务」，其中 Exa、Tavily、Firecrawl、Parallel、TinyFish 是可选的外部服务。

## 全程烹饪指导

菜谱确定后，向 Cook 请求全程指导。Cook 使用保存的菜谱版本生成程序谱和动作谱，成功后终端自动打开指导界面。界面占终端宽高约四分之三；当前动作使用大字，随窗口和文字长度自动换行、缩小，完整显示，不分页。Enter 确认当前动作完成，P 暂停或恢复，Q 结束，Esc 暂停并返回对话。

输入 `/cooking` 或点击右侧栏的「返回烹饪引导」按钮可重新打开界面，暂停状态保持不变。窄窗口没有侧栏时，输入框上方提供相同入口。也可以自然地告诉 Cook 想回看指导或接着做菜：Cook 结合对话和实际进度识别意图，回看只打开界面，继续烹饪则恢复原任务、步骤与累计计时；继续其他话题不触发烹饪恢复。重新进入无需再次生成程序谱和动作谱。

持续动作依据传感器条件或推荐时长自动推进，界面区分两种原因。没有设备时使用手动确认和推荐时长，不显示虚构的观测结果。服务重启后的指导会保持暂停，需要核对实际进度再恢复。

引导界面固定显示摄像头、温度、声音和空气的连接状态灯，窄窗口会自动换行。绿灯表示在线，红灯表示离线，黄灯表示连接中；未配置、停用或状态未知显示灰灯。完成后显示“本次烹饪引导已完毕”。返回对话时，后台将实际结束结果送入 Cook 的会话队列，由 Cook 简短反馈；中途结束会单独标明，重复返回或重启 CLI 不会重复添加结果。已完成或已结束的任务不再显示侧栏按钮和输入框旁的恢复入口。

源码更新后需要退出旧 CLI 并重新启动，旧进程不会载入新的终端界面。可在项目根目录运行 `bun run dev --standalone` 使用当前源码。

启用 Settings →「模型服务」→「语音合成 TTS」后，当前动作和提醒会通过本机扬声器播报。默认采用学校接口的“新闻女声” `female_news`，语速1倍；音色菜单也提供甜美女声、丽娃、文艺女声及自定义 ID，语速可在0.25至4倍之间设置。音色描述和接口参数见[学校 TTS 文档](https://developer.ecnu.edu.cn/vitepress/llm/api/audio.html)。

指导界面按 V 静音或取消静音，按 R 重播当前动作。切步、暂停和结束会取消旧语音，不排队补读已经过去的动作。TTS 失败只显示提示，步骤操作继续运行。音频通过内存播放，不保存语音文件；实际声音从运行 CLI 的设备输出。

## 个人烹饪记忆

做菜后可以直接评价，例如“这次鸡蛋有点老，酱油味太重”。Cook 使用 `cooking_memory` 保存用户原话、主题、适用菜品或技法，并关联匹配的实际烹饪任务、菜谱修订版本、配方全文和完成方式。调整建议单独标记为待验证的建议，不会当成用户说过的话或已经证实的原因。记忆持久化在本机数据库，不上传到公共菜谱库；重启和新建对话后仍能使用。

之后推荐或制定相关菜谱时，Cook 召回个人经验；菜谱工具也会独立读取相关记忆，将其传入推荐、适配评估、个性化及改动说明阶段。现有参考配方继续保留。当前明确要求优先于历史偏好；相似菜品的经验需要核对食材、锅具和做法是否适用。更新记忆会使相关任务中的旧适配缓存失效，新的调整仍需走菜谱校验。

“我一直不喜欢甜口”可作为长期偏好；“今天想清淡一点”属于当次要求，不自动变成永久偏好。一道菜的单次体验必须限定菜品或技法。可以直接说“看看你记住了什么”“把那条鸡蛋偏老的评价改成……”“忘记我的甜口偏好”，让 Cook 查询、修正或删除相应记录；删除长期记忆不会同时删除原始聊天和已保存的菜谱。

写入个人记忆前，工具使用已配置的文本模型独立检查完整用户原话和相关对话中的时效、归属及是否真的报告了做菜结果，避免把某一天的计划、客人的口味或假设写成自己的持续偏好或经历；长期偏好还需核对 `lasting_evidence` 是否来自用户原话。核对超时或结果不明确时不写入，Cook 会说明未保存。该检查不占用烹饪执行器的计时和判定锁。

默认使用“本机默认用户”档案。明确说“切换到小王”等身份切换指令后，可建立或选择另一个本机个人档案，其他已绑定的对话保持原档案，后续新对话采用新选择；内部子任务继承父对话的档案。客人或家人的名字、口味不自动切换用户。档案是本机的记忆分组，不是有独立登录认证的多用户账号系统。

记录评价与调整建议需要 Cook 正确理解语义并调用工具；持久化成功、原话核对、档案隔离、去重以及菜谱工具读取由代码负责。这项能力不训练或更新模型参数。当前召回基于菜名别名、食材/技法标签和档案内的相关性匹配，不宣称使用向量检索或已验证的因果学习。

## 摄像头与传感器

Settings →「摄像头与传感器」分别设置 RTSP 摄像头、温度传感器、声音强度传感器和空气质量传感器。设备默认停用，需自行填写地址或串口并启用。摄像头密码可包含在 RTSP 地址中输入，保存时会拆入凭据存储；也可以单独设置密码。FFmpeg 路径留空使用系统 PATH 中的 `ffmpeg`，或填写本机可执行文件路径。

状态灯根据实际收到的有效视频帧或传感器样本变化：绿色表示最近收到有效数据，红色表示失败或数据超时，黄色表示连接中，灰色表示未配置或停用。打开端口本身不会点亮绿灯。设备页每秒刷新，Ctrl+R 重新连接所选设备。

默认参数保留原脚本的设置：温度 115200 baud、2000 ms 超时、500 ms 采样；声音 9600 baud、1000 ms 超时、500 ms 采样；空气 9600 baud、1000 ms 超时、主动上传，预计间隔 1000 ms。串口采样间隔在本次读取结束后计时。空气的预计间隔只用于缓存容量，不额外改变传感器上传频率。相同串口不能同时分配给两个启用的传感器。

## 调试记录

Settings →「传感器调试模式」，默认关闭。关闭时继续在有界内存中采样、缓存和判定，不创建传感器记录目录。开启后才保存摄像头 JPEG、温度 CSV/热力图、声音和空气样本及翻炒警告。保存目录可以自定义，启用时需填写绝对路径。

切换调试模式不会重启采集线程或清空缓存。关闭后停止新增记录，已保存的文件保留。调试热力图使用 OpenCV 色图；它不参与温度或翻炒判定。原始 Python 脚本留作迁移对照，单独运行那些脚本仍使用它们原有的记录设置。

摄像头和串口运行代码位于 `packages/core/src/cooking/devices/`，不调用 Python。源码在 Node 主进程中直接使用串口驱动；Bun 和封装后的可执行文件通过 Node.js 子进程使用随包附带的串口模块与原生驱动。需要 PATH 中有 Node.js 22 或更新版本，也可用 `OPENCOOK_NODE_PATH` 指定 Node 可执行文件。摄像头使用系统 FFmpeg，或在设备设置中填写完整的 FFmpeg 路径；安装包不附带旧版 FFmpeg。Docker 镜像会安装 Node.js 和 FFmpeg。

`packages/cli/script/device-smoke.py` 使用真实伪串口验证三个传感器的读写、状态值，以及调试默认关闭、开启保存、关闭停止和写盘失败不打断采样的行为。它是 Linux/macOS 的测试脚本，不是运行时依赖；可传入回环 RTSP 流进一步检查摄像头与 JPEG 编码。真实硬件及厨房场景仍需另行验收。

## 迁移验证环境

开发者可创建包含 Python 3.11、NumPy、OpenCV、pyserial 和 Matplotlib 的独立测试环境，用于执行原始算法作对照；它不是产品依赖。已有对照数据随测试夹具提供，重新生成时需自行准备原 Python 项目：

```sh
conda create -n opencook-sensor-test python=3.11 numpy opencv pyserial matplotlib -c conda-forge
conda activate opencook-sensor-test
cd packages/core
python script/sensor-reference.py /absolute/path/to/original/OpenCook > test/fixture/sensors.json
bun run test test/sensors.test.ts test/sensor-equivalence.test.ts
```

生成器只执行原脚本中选定的 AST 定义，避免导入时启动硬件或写入历史目录。固定数据记录源文件摘要；测试覆盖协议字节、温度矩阵、五分区、六帧窗口和视觉相关性。原生 OpenCV 与 WASM 的数值按浮点容差比较，并核对测试样例的报警结论。

## 导入烹饪语料

从项目 `packages/core` 目录运行：

```sh
bun script/knowledge-import.ts /absolute/path/curated-passages.json
```

输入是 JSON 数组。每条资料包含以下字段：

| 字段                         | 内容                                                   |
| ---------------------------- | ------------------------------------------------------ |
| `id`                         | 稳定且唯一的段落 ID；重复导入相同 ID 会更新对应资料    |
| `title`、`author`、`edition` | 可核实的书名、作者、版次                               |
| `locator`                    | 页码、章节或其他可定位位置                             |
| `source`                     | 原始资料位置或来源标识                                 |
| `text`                       | 可独立理解的原文段落                                   |
| `tags`                       | 菜名、原料、技法、地域等检索标签数组                   |
| `recipe`                     | 可选，经过核对的结构化菜谱，格式见 `cooking/recipe.ts` |

先提取文字、按菜谱或知识主题切分，再核对出处和内容，最后导入。避免把整本书作为一条资料；同一配方的原料与步骤应保持关联。保留版本差异，不拼接来源不一致的配方。导入脚本不会自动验证出版物权威性、OCR 准确性或使用授权。

资料保存在当前服务的持久化 KV/SQLite 中。导入进程必须使用与聊天服务相同的数据目录和运行用户。

当前检索使用中文双字词及英文词的本地词法匹配，按标题、标签和正文打分，返回有限数量的原文及元数据。尚未接入 embedding、向量索引、重排服务或自动 PDF/OCR 导入。正式书籍语料尚未导入；测试资料不会作为产品默认知识库发布。

## 网页证据

`webfetch` 成功读取文本后，记录当前会话中的页面证据。菜谱工具通过 `evidence_urls` 读取这些记录。最多接受五个 URL；不能拿另一会话的记录或未经读取的链接充当证据。记录保留最多 30000 个字符，超出部分明确标记截断。来源是否充分仍由领域提取与 Cook 判断。

## 烹饪异常监测与应急中断

仅在有运行或暂停中的烹饪引导时启动监测；结束后取消监测和未完成的视觉请求。着火、糊锅分别轮询，间隔 2 秒，阳性提醒独立冷却 10 秒。糊锅沿用原 Python 的烟雾阈值：空气传感器有新鲜有效数据且浓度至少 9 mg/m³ 时才请求视觉判断。着火检测只依赖有效摄像头，不依赖空气传感器；正常炉头火焰不应判作锅内着火。缺少设备或视觉请求失败会显示监测不可用或失败，不当作安全结论。

阳性结果立即冻结普通步骤与计时，在原步骤前显示独立应急步骤。着火优先于糊锅，可以升级已经显示的糊锅应急步骤；重复报警不重复插入。应急步骤靠用户确认，既不依赖普通步骤计时器，也不标记被中断的步骤已经完成。旧步骤和旧应急编号的确认请求会被拒绝。

在引导页完成应急操作后，按 `S` 明确确认现场安全，普通引导仍保持暂停；核对锅内状态和被中断操作后再恢复。服务重启保留未完成应急状态。这里提供操作指导，不会操作实体炉灶；视觉判定可能漏报或误报，不能替代现场照看。应急提示参考[美国消防局厨房防火指引](https://www.usfa.fema.gov/prevention/home-fires/prevent-fires/cooking/)及[北京市应急管理局油锅起火指引](https://yjglj.beijing.gov.cn/art/2015/4/13/art_3942_243698.html)。

异常事件保存在烹饪运行状态中，返回聊天时一并反馈给 Cook；调试关闭时不保存传感器图片和调试日志，开启后才保存异常调试记录。
