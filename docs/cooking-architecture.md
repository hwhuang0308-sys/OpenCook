# 烹饪对话与菜谱任务

Cook 负责理解自然对话、归纳已确认条件、澄清关键缺口、安排复杂任务和选择工具。规划属于 Cook 的日常能力。产品只有一个可见主角色，内部标识为 `cook`。

## 职责边界

| 层       | 职责                                                                                  | 实现位置                                           |
| -------- | ------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 对话     | 目标理解、交互节奏、条件变化、文档任务、来源选择                                      | `packages/core/src/session/runner/prompt/cook.txt` |
| 菜谱领域 | 分阶段提示词、结构化输出、校验、任务持久化                                            | `packages/core/src/cooking/`                       |
| 领域工具 | 注册 `recipe_task`、`search_cooking_knowledge`、`cooking_session`，执行叶节点权限检查 | `packages/core/src/plugin/cooking.ts`              |
| 检索     | 本地语料检索、出处元数据、当前会话网页证据                                            | `packages/core/src/cooking/knowledge.ts`           |
| 模型     | 用户配置的对话与视觉路由、按用途保存的模型配置及本地凭据                              | `packages/core/src/plugin/model-runtime.ts`        |
| 对话执行 | 持久化消息、逐步模型调用、工具执行、恢复、摘要                                        | `packages/core/src/session/`                       |

没有增加第二个工具调用循环。领域阶段调用已有 Generate 服务取得结构化内容，主对话继续使用已有的持久化执行机制。

`requirements.ts` 在菜谱开发和启动引导的边界整理真实用户消息与问答工具的实际答案，缓存已处理的消息来源。新消息只更新受影响的条件，不重新解释旧回答。每个条件变化需要能核对的原话；库存数量还需原话中的数词、单位证明，不能把配方用量变成库存。普通问候、知识问答和联网研究不会自动运行此阶段。

`conditions` 工具参数支持局部更新：省略字段保留旧值，传入列表替换该列表，`servings`/`minutes` 的 `null` 清除旧限制。生产入口使用独立整理的已确认条件，工具调用中猜出的数量、偏好和设备不成为用户事实。`equipment` 表示已知设备；只有明确的排他限制才设置 `equipment_only`。油、水、盐等不会因为被放进不同清单分类而被错误判为缺货。

适配评估只将不可合理默认的个人事实或显式条件冲突退回用户。用量、火候、加料顺序和油量分配由菜谱决定。`review.txt` 在生成工具内部检查实际违约项并要求修复，不再创建新问题；有限次修复仍失败时，菜谱保持未就绪。工具显式返回 `ready_for_guidance` 与 `next_action`，相同请求复用结果；提示词规则版本变化会使旧评估失效，旧会话不再复用过时的追问。

Cook 每次模型步骤都可读取实际菜谱与引导状态，包含从一开始计数的当前步骤。没有新增用户输入却对同一任务连续返回六次阻塞结果时，当次响应停止继续调用菜谱及提问工具；默认模型步骤上限为24。开始引导时再次核对最新用户条件，拒绝把更改前的菜谱交给执行器。开始、打开或恢复后只简短确认，步骤由专用界面推进。

状态投影明确包含当前阶段、候选菜、原参考配方的名称/份量/来源、当前是否为改造版本，以及最新消息是否已经完成要求核对。读取旧配方的 `get` 不算重新核对新要求。工具的 `transition` 报告实际变更字段、同菜继续/换菜/换参考的原因、参考是否复用和实际资料选择；它是工具响应中的派生信息，不增加独立的规划角色或持久化工作流。

收到新要求时，Cook先区分目标变化与条件变化：同菜改口味、人数或设备通常复用参考并更新受影响的配方；换菜清除旧参考；明确换来源时读取新资料并替换参考；追问原理、研究或排版请求保留已有配方。新条件形成知识缺口时补充该缺口，不能因一次改口味就重新执行整个推荐与检索流程。菜谱评估产生的问题也经过必要性核对，常规油盐顺序等问题在任务进入“待澄清”之前被移除，避免只拦截表单却仍被缓存问题卡住。

明确的引导请求与引用原话独立保存为待完成动作，不混入口味条件。菜谱准备完成后返回 `next_action=start_guidance`，实际启动成功才消费这项请求。拒绝或要求先预览会清除请求；引用不准确时先修复引用，不能悄悄丢失用户的启动意愿。提问工具在展示表单前筛选必要问题，常规烹饪选择不会作为一轮用户问答；未展示的问题也不会伪造用户回答。临时偏好未进入长期记忆属于正常的 `not_retained` 结果，不作为工具故障触发反复保存。

引导工具仅向模型返回运行ID、菜谱版本、实际当前步骤和界面状态，完整程序谱与动作谱保留在执行服务中。暂停、恢复、停止按运行ID控制，不因读取步骤后发生推进而被拒绝；确认物理动作仍严格核对步骤索引。编译时将中小火等写法归入执行器既有四档火力，避免程序谱与动作谱对火力名称的校验互相冲突。

个人经验由 `cooking/memory.ts` 持久化，`cooking_memory` 提供查询、保存、修正、删除和本机档案切换。写入需要核对本轮真实用户消息中的原话；烹饪经历关联实际执行记录与菜谱版本。用户评价和模型提出的调整假设分别保存。Cook 的上下文钩子只注入当前档案的相关记忆，菜谱工具在推荐和适配阶段独立读取同一份记忆，当前要求优先。共享知识库不混入个人体验。档案隔离覆盖新对话及子对话的继承，属于本机分组而非账号认证；操作说明见 `operations.md`。

## 按需选择阶段

| 用户意图或当前状态               | 操作                       | 停止条件                             |
| -------------------------------- | -------------------------- | ------------------------------------ |
| 只要菜名建议                     | `recipe_task.suggest`      | 返回候选菜名和理由，等待进一步需求   |
| 已指定菜品                       | `recipe_task.reference`    | 返回有出处且适用的参考菜谱           |
| 已提供菜谱                       | `provided_recipe`          | 保留用户提供的版本及其来源性质       |
| 参考菜谱符合条件                 | 返回参考菜谱               | 不生成额外的个性化版本               |
| 份量、库存、设备或明确偏好不匹配 | `recipe_task.personalize`  | 通过校验并说明实际改动               |
| 继续使用已有结果                 | `recipe_task.get`          | 返回保存的版本和待解决问题           |
| 关键个人事实不清楚               | 返回 `needs_clarification` | Cook 询问最有影响的一至三个问题      |
| 来源不足                         | 返回 `needs_evidence`      | 补充可靠来源，或明确允许一般知识草案 |

情绪与地域以用户原话保存在条件中，用于推荐排序、表达方式和必要的口味判断。“想家”和“北京人”不等于已知其家庭配方，也不自动要求改造一道已经合适的菜。

每个任务保存会话 ID、任务 ID、修订号、条件快照、候选菜、参考版本、调整版本、来源和说明。修改条件会使旧调整失效；更换菜品会清除旧参考。回到推荐阶段会清除旧的选菜和菜谱结果，保留新候选及其来源。任务和网页证据均不能跨会话读取。

## 原工作流规则的归属

- 菜名生成规则保存在 `prompts/dish.txt`；生成的纯中文菜名最长六字，保留用户指定菜名。
- 参考菜谱规则保存在 `prompts/reference.txt`。优先采用一个可辨认来源的完整配方；缺乏资料时可以报告缺口。
- 个性化规则保存在 `prompts/personalize.txt`。库存限制包含油、水、调料和点缀；不要求使用所有库存。
- 偏好和饮食要求由 `prompts/assessment.txt` 评估；`prompts/review.txt` 检查调整结果并在内部修复。不能承诺医疗结果。
- 改动说明由 `prompts/adjustments.txt` 生成，最多 300 字；没有实质变化时使用既定说明。
- 代码校验正数用量、明确单位、原料与步骤关联、库存范围、已知库存数量、常见单位换算、排除原料、份量、设备、时间和来源 ID。
- `recipe.ts` 统一渲染“所需食材：”“所需调料：”“烹饪步骤：”三段。出处、估算标记、设备及调整说明单独呈现。
- 格式或确定性校验失败，每阶段最多尝试三次。未知库存量作为未解决信息返回，不能当作无限库存。
- 参考提取分别返回 `ready + recipe + notes` 或 `needs_evidence + gaps`。常规油盐用量、份量和总时长的估算放入说明，不阻塞完整配方。相同网页内容复用已保存的提取结果或阻塞原因；只有新证据才重新提取，条件修改不绕过证据检查。

语义判断仍依赖模型。精确名称校验不能替代对复合食材、过敏原和实际烹饪可行性的完整审核。

## 获取知识

消息进入模型前不自动检索。Cook 在现有对话循环里结合上下文理解目标、待确认事项和来源要求，决定直接回答、澄清或调用工具，不增加独立的意图分类角色。

| 请求或信息条件                     | 来源选择                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------ |
| 问候、闲聊、对上个问题的确认       | 直接回应，或继续已经确认的任务；仅在下一项工作需要新证据时检索                 |
| 基于已有信息改写、排版、计算       | 使用对话及已有资料                                                             |
| 明确要求联网搜索、比较网上做法     | 直接 `websearch`，再用 `webfetch` 阅读相关原文                                 |
| 指定书籍、文件或 URL               | 先读取指定材料；遵守不联网等限制                                               |
| 未指定来源，需要烹饪知识或参考配方 | 优先书库；判断检索资料是否相关且足够                                           |
| 资料不足                           | 稳定、低风险的问题可结合一般知识回答；时效问题、特定来源或重要知识缺口联网核实 |

提到菜名不等于要求生成菜谱。搜索比较可以只返回研究结果；只有需要推荐菜品、取得或调整菜谱时，才调用 `recipe_task` 的对应阶段。

菜谱工具的 `source` 参数使来源选择落实到代码：

- `auto`（默认）：复用同菜品的已有参考，或采用 `provided_recipe` / 已读取的 `evidence_urls`；需要新参考且没有指定资料时才查书库。只推荐菜名默认不检索。
- `library`：明确检索书库，也可用于有书库依据的菜名推荐。
- `web`：只使用 `evidence_urls` 对应的当前会话网页；缺少已读取的网页则返回 `needs_evidence`，不会退回书库版本或无来源草案。

明确指定 `library` / `web` 或提供新资料会重新选择参考版本；只修改份量等条件时使用默认来源以保留原参考。未执行书库检索时，新的证据记录使用 `not_searched`，不会伪装成“书库为空”。复用已有参考时保留其原始检索和出处记录。

书库实际检索分别返回 `empty_library`、`no_match`、`ready`。`ready` 只表示有命中；Cook 仍需判断资料是否支持结论。网页必须先成功读取，后端才接受其 URL 为菜谱证据，且只接受当前会话已有的页面记录。普通网页不会自动写入权威书库。

## 做菜指导

用户接受菜谱后，Cook 可以主动提出全程指导。接受菜谱、同意开始指导和完成物理动作分别记录和理解。明确要求“一步步带我做”已经表达启动意愿。

`cooking_session.start` 绑定已就绪菜谱的任务 ID 和修订号。`compiler.ts` 按原 Python 工作流的动作拆分、模板及传感器规则编写 `prompts/program.txt`、`prompts/actions.txt`，依次生成程序谱和动作谱；模型均来自用户配置的文本服务。模型输出结构化步骤及动词槽位，由代码生成固定格式，并依据持续步骤的明确火力生成独立调火动作。代码检查编号、动作模板、设备阈值和条件逻辑，动作谱直接继承程序谱的 until 与推荐时长。失败最多修正三次，不跳过坏步骤；准备完成时再次检查菜谱修订，拒绝过期版本。

`execution.ts` 是后台的确定性执行服务。瞬时动作由用户按 Enter 确认；持续动作保留原执行器的“传感器条件满足或达到推荐时长”推进规则。记录明确区分 `confirmed`、`sensor` 和 `duration`；推荐时长结束不能表述成传感器已观测到完成。设备未连接时显示实际状态，仍可手动确认或使用推荐时长。

`conditions.ts` 保留锅/油温连续达标、食材椭圆区与冷点双阈值累计达标、声音前后窗口差值和两次视觉判断规则。视觉使用配置的多模态服务，不使用对话模型。翻炒提醒保留最短三秒展示与三秒冷却。采集协议和采样模块未改动。原异常监测中的着火、糊锅模型调用被注释，本次不启用新的自动异常检测。

终端 `cooking-guide.tsx` 在开始后自动打开独立指导界面，显示当前动作、下一动作、条件、计时、设备状态及提醒。按键或按钮通过 API 操作执行服务，不经过模型。P 暂停/恢复，Q 结束，Esc 暂停并返回对话；对话中可打开原指导。后台持久化动作谱、当前步骤与完成原因，服务重启后恢复为暂停，用户核对现场后才能继续。旧版本步骤确认会被拒绝，结束后停止推进。

Cook 可在用户明确报告当前动作完成时通过工具确认，也可按用户要求暂停、恢复或结束；不得同时在聊天中维护另一套步骤。烹饪中途换菜的后续动作重规划尚未接入；实体设备的实际联调需在设备连接后验证。

### 语音播报

`speech.ts` 使用已配置的 TTS 模型及凭据调用 `/audio/speech`，默认音色 `female_sweet`、语速1倍。它只合成当前执行会话的当前动作或提醒，在请求前后均检查会话、动作和运行状态，过期结果返回 `obsolete`。单次请求最长20秒，失败不改变步骤状态。模型设置支持音色与语速，已有配置不需要迁移。

语音在终端所在机器播放，由 `CookingNarration` 管理独立的异步播放任务。待播槽位仅保留最新一项，切步时中断旧请求与旧播放，等待资源释放后播放最新步骤；即便旧网络请求忽略取消、较晚返回，其结果也不播放。相同状态轮询不重复播报，提醒可以抢占步骤播报。暂停、结束、静音、切换会话或关闭界面时取消播报；网络失联时停止旧播报。语音请求与播放均不占用执行锁，不阻塞计时或动作确认。

MP3 在内存中传输与播放，不写入用户磁盘，不累积音频缓存。终端 V 切换静音，R 重播当前动作。旧 Python 的语音锁能够避免重叠，但会排队朗读过期步骤；新实现保留互斥播放，并按当前执行状态取消过期语音。
